# Decision Record: RustSec Remediation and Storage Runtime

**Date:** 2026-10-04
**Status:** Approved by repository owner choices in this session
**Related plan:** [`docs/roadmap/rustsec-zero-exception-remediation-plan.md`](../roadmap/rustsec-zero-exception-remediation-plan.md)
**Context:** PR #108, branch `fix/rocinante-readiness-remediation`

## Decisions

### Require zero active RustSec findings, without exceptions

The remediation is complete only when a refreshed RustSec audit of every
supported lockfile passes `--deny warnings` with no ignore entries and no
vulnerability, unsoundness, or unmaintained-package warnings. The 17 overdue
registry records are not all live advisories: eight IDs were withdrawn and five
refer to packages absent from the lockfile; four warnings remain in the current
unfiltered graph. Remove the 13 obsolete records with evidence and remediate
the four live findings. Do not renew review dates or infer security-owner
acceptance.

**Rationale:** The governance failure is a time check on audit exceptions, not
a current vulnerability scan. A date renewal would not repair the dependency
graph. A zero-exception audit provides a repeatable and unambiguous completion
condition.

### Use SQLite for ingestion and DuckDB for analytics

SQLite replaces Sled as the embedded ingestion store; DuckDB remains the
analytics store. This explicitly supersedes the older Badger-only ingestion
destination in `docs/roadmap/architecture.html`. Preserve supported commands,
payloads, authorization, data, and behavior while changing the storage adapter
and backend configuration.

**Rationale:** Sled 0.34.7 brings the current `fxhash` and `instant` warnings.
The repository already has `rusqlite` and bundled SQLite. This removes the
application's Sled dependency without introducing a separate service runtime.
Preserving data is required, so the temporary migration reader remains in the
audited workspace and must itself have a clean dependency graph.

### Keep DuckDB embedded but require official prebuilt libraries

Keep the Rust DuckDB API and dynamically link official precompiled native
libraries matching the Rust binding release. Record artifact origin, version,
checksum, license, and supported targets. Fail on missing or mismatched
artifacts; never compile DuckDB from source or silently use an unverified
system library.

**Rationale:** Existing analytical behavior uses the embedded API. Prebuilt
libraries preserve that interface while avoiding the current bundled source
build. Version and checksum pinning makes the native binary verifiable and
reproducible across CI and installed applications.

Package the staged native library with the application so installed builds do
not depend on Cargo's local cache. Linux stores `libduckdb.so` in the per-user
Rocinante library directory and sets an `$ORIGIN` path. macOS places
`libduckdb.dylib` in the app's `Contents/Frameworks` directory and resolves it
through `@executable_path`; release signing must happen after this rewrite.
Windows places `duckdb.dll` beside the installed executable.

**Rationale:** A dynamic link to a verified release is insufficient if the
installed app still points into a developer's target directory. Packaging the
same checksummed artifact beside the executable keeps runtime behavior
portable and makes the no-source-build requirement testable after install.

The Tauri bundle uses the resource directory as the runtime location on each
platform: Linux resolves from `$ORIGIN/../lib/rocinante-repo-analyzer`, macOS
resolves from `@executable_path/../Resources`, and Windows loads the DLL next
to the executable. The `beforeBuildCommand` provisions the checksum-verified
prebuilt; the `beforeBundleCommand` stages it and rewrites the loader path.
CI builds and inspects the actual Linux, macOS, and Windows Tauri packages.

**Rationale:** A P1 review finding on PR #108 identified that dynamic linking
without packaging the native library would prevent an installed Tauri app
from starting on a machine without a Cargo cache. The package must carry the
same verified binary used during compilation; source builds and unverified
fallback libraries remain forbidden.

### Retire Tauri/GTK after native-shell parity

Promote the GTK-free shell and remove Tauri/Wry from the supported application
workspace after existing desktop behavior passes parity validation.
Repository-folder selection satisfies the chooser requirement; no new file
import workflow is part of this remediation.

**Rationale:** The current host graph contains `glib 0.18.5` and
`proc-macro-error 1.0.4`. The already selected host-migration direction
eliminates that dependency path rather than relying on a major GLib ecosystem
upgrade that does not match the current GTK stack. Parity gates protect user
behavior during the host change.

## SQLite migration implementation update (2026-10-04)

The local worktree now replaces application Sled ingestion with SQLite WAL in
`rocinante-storage`. The database is stored at
`<ROCINANTE_KV_PATH>/ingestion.sqlite3`; raw event writes use durable SQLite
transactions, and binary key/value prefix scans retain byte ordering. DuckDB
promotion records telemetry, baseline data, and a unique source-event receipt
in one transaction before SQLite deletes the pending event. Replaying after a
DuckDB commit and before the SQLite acknowledgement therefore skips duplicate
analytics rows.

The default backend is now `SqliteWal`. Rust command names and payload schemas
remain unchanged. Explicit `BadgerSidecar` configuration remains available;
`SledTransitional` is retained as a recognizable legacy enum value but returns
an actionable error directing callers to SQLite WAL. Startup also refuses to
create a SQLite store when it detects the old Sled directory markers. These
compatibility checks prevent legacy data from being silently ignored.

**Rationale:** the updated lockfile no longer contains `sled`, `fxhash`, or
`instant`, removing the two associated RustSec warnings without suppressions.
Keeping the old enum value lets existing callers receive an actionable error
instead of a deserialization failure. Preserving explicit sidecar configuration
limits the behavior change to the default backend and removed Sled mode.
Legacy Sled data still requires the Phase 3 migration utility before upgrade.

Local evidence: the workspace tests excluding the Tauri adapter pass 83 tests;
the root storage, transport, backend, admin-ingestion, Tauri-command, and
README/API test binaries pass 17, 5, 5, 2, 5, and 1 tests with the verified
staged DuckDB runtime. Nine storage-specific tests are included in the workspace
run. Root `cargo check --tests` passes, and strict workspace Clippy passes for
the extracted crates. The Cargo command for root integration tests did not
return and was interrupted after the directly invoked binaries passed. A

RustSec revision `ef6173cbc5c50ec8166f9a5b28f07834144373ee` (2026-10-03)

## Consequences and superseded direction

- The application dependency graph, backend configuration, workspace tests,
  and architecture documentation will change. Rust command and payload
  contracts remain stable unless an incompatibility is discovered and recorded.
- A Sled compatibility reader adds migration and audit work; it cannot be
  omitted because legacy data must be preserved.
- SQLite's use is limited to ingestion. DuckDB continues to serve analytical
  queries and snapshots through its Rust API and prebuilt native library.
- The Badger-only destination, active 17-entry exception rationale, and
  Tauri-as-production-host statements in older docs are superseded by this
  record and plan. Update those documents when implementation evidence exists.
- PR #108 remains blocked until the zero-exception audit and the required
  workspace, packaging, and platform checks pass. Scheduled audits must block
  later releases when RustSec publishes a new applicable finding.
