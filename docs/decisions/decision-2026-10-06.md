# Decision — Keep the macOS explicit-quit candidate gated on installed-app acceptance

**Date:** 2026-10-06
**Status:** Accepted as the current implementation candidate; release acceptance remains open.

## Context

The previous macOS viewport-close path could close the window while leaving the application process resident after a Quit action. The merged source now persists shell state, flushes storage, drops the tray icon, and calls `std::process::exit(0)` for explicit macOS Quit. Linux and Windows retain eframe viewport close, and ordinary close-to-tray remains a hide action.

PR #112's final head `bb2d1700e4ae0c1663df140336f2f2ededbd0963` passed CI `37417428474`, Security `37417428663`, and Dependency Review `37417428598`. These automated results verify the hosted source and package lanes. The latest recorded manual Show attempt timed out at an earlier code head without observing the Show callback. The user also reported that the app was unstable and did not come up cleanly, but no exact artifact, error, or crash evidence identifies the cause.

## Decision and rationale

Keep the persisted-state hard-exit helper as the current candidate because it follows the observed resident-process failure and has passed exact-head hosted checks. Do not claim the desktop is ready or change the shutdown strategy again until an interactive installed build is reproduced and inspected. This keeps the known Quit behavior correction while preventing automated checks or an earlier timeout from being mistaken for physical UI evidence.

DuckDB remains an official checksum-verified prebuilt binary. Rebuilding it from source is prohibited.

## Required evidence before closure

- Current signed installed build starts cleanly through Launch Services. If it fails, record the exact dialog/log/crash evidence before assigning cause.
- Physical Show callback and foreground visible restoration pass; physical Quit callback is witnessed and the process exits after the save/flush sequence.
- Cold/warm URL delivery and saved-state restart pass on the same build.
- Bundled DuckDB checksum, library name, loader path, and code signature checks pass.
- Exact-build hosted CI, Security, and Dependency Review remain green.

See [the dated shutdown remediation plan](../roadmap/macos-native-shutdown-remediation-2026-10-06.md) for execution steps. Until the criteria pass, keep manual macOS launch, tray, foreground, and restart acceptance open.

## Decision — Define the browser preview audience and command fallback

**Date:** 2026-10-06  
**Status:** Accepted; responsive validation remains open.

### Context

The 2026-10-05 frontend UX panel questioned whether a Tauri-specific runtime failure is appropriate in the browser surface. The current [UI codemap](../ui/codemap.md) defines React/Vite as the dashboard preview and headless UI validation harness. The supported desktop host is the Rust eframe/winit shell. The Tauri adapter remains only for compatibility tests and does not indicate a packaged Tauri runtime.

### Decision and rationale

Treat the React/Vite application as a browser preview and validation harness, not as the supported desktop application. The browser fallback should name the actual context and explain the limitation. Changed the fallback to “Desktop command runtime not detected. Admin commands are unavailable in the browser preview.” This accurately describes the supported host boundary without implying that production desktop uses Tauri.

### Validation

Unit and browser assertions cover the revised fallback. Hosted exact-head checks are pending. UX-13 remains open until browser tasks are observed at 320, 360, 768, 1024, and 1280 CSS-pixel widths and at 200% zoom; no responsive defect is asserted before that evidence. The test PR currently checks overflow and import/admin task reachability at the five CSS widths. DuckDB remains a checksum-verified prebuilt binary and is never rebuilt from source.
